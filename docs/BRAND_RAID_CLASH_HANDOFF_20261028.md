### R2-1. 사용자 추가 확정 ✅ (2026-10-28)

### R2-2. 운영 DB·저장소 재검증 결과 (2026-10-28, 읽기 전용)

**R2-2a. 원본 위치 — 가장 중요**
- 전투 엔진 v1.5(`raid_combat_tick`, `raid_advance_patterns`, `raid_apply_barrier_damage`, `raid_combat_states`, `raid_pattern_runs` 등)의 SQL은 **GitHub 저장소와 Git 전체 기록(556커밋) 어디에도 없다.** 운영 DB에만 존재한다.
- 저장소의 `submit_raid_tap_batch`·`teacher_pause_raid`·`teacher_resume_raid`·`get_raid_battle_state`는 9월 v1 버전이며 운영본과 다르다(운영 `submit_raid_tap_batch` 36,396자).
- **착수 0단계:** 수정 대상 함수의 운영 원본을 `pg_get_functiondef`로 저장소(`supabase/production_snapshots/`)와 DB 백업 표에 동시 보관한 뒤 작업한다. 모든 수정 마이그레이션은 10-17 속성 패치와 같은 방식(원본 읽기 → 정확한 문자열 1곳 치환 → 원본 불일치 시 전체 중단)을 쓴다.

**R2-2b. 문서 8.2장과 일치 확인 ✅**
- `raid_apply_barrier_damage`: 피해량 = `p_fixed_damage + ROUND(barrier_max_hp × p_barrier_ratio)` → **최대 HP 기준 확인.** 실패 페널티는 반드시 `p_fixed_damage = ROUND(현재 잔여 × 0.20)`, `p_barrier_ratio = 0`으로 호출. 이 함수는 레이드가 ACTIVE가 아니거나 방벽이 꺼져 있으면 **예외를 던진다** → 격돌은 방벽 ON 레이드에서만 활성화 허용(최근 레이드 10개 모두 방벽 ON).
- 잔여 20% 차감은 잔여 ≥ 1이면 0이 되지 않으므로 **격돌 실패만으로 방벽 붕괴(=레이드 실패)는 발생하지 않는다.**
- `teacher_resume_raid`: `raids.starts_at/ends_at`, ACTIVE `raid_pattern_runs.started_at/ends_at`, `next_boss_attack_at`, `groggy_until`을 일시정지 길이만큼 이동하고 `metadata.raid_total_paused_seconds`에 누적 → **격돌 재개도 같은 필드 목록을 공용 헬퍼로 이동**한다.
- `raid_combat_tick`: advisory lock `77115`(틱 단일화), `77116`(공격 배치와 공용 변경 게이트), 800ms 스로틀, `raid_advance_patterns` 실행 후 보스 일반 공격 판정. **학생 참가자만 호출 가능**(교사 화면은 틱을 돌리지 않음).
- `submit_raid_tap_batch`: `client_batch_id` 멱등, `77116` 시도 실패·`FOR UPDATE NOWAIT` 실패 시 `busy` 반환, 탭마다 `v_hp_working`을 줄이는 반복문 → **50% 최초 통과 탭을 반복문 안에서 정확히 잡을 수 있다.**
- `raid_e3_finish_pattern_success`: 그로기를 덮어써서 시작 → 격돌에 재사용 금지 ✓.
- 격돌·QTE 전용 테이블 없음 ✓.

**R2-2c. 새로 확인된 사실 (본문에 없던 것)**
1. **레이드에 제한시간이 없다.** 최근 레이드의 `ends_at`이 모두 NULL. 레이드는 보스 HP 0(성공) 또는 방벽 붕괴(실패)로만 끝난다. 즉 **방벽이 사실상 전투 시계**다. 최근 8회 중 3회(id 65·66·67)는 보스 HP 52~64%에서 방벽이 무너져 **50%에 도달하지 못했다** → 그런 레이드에서는 격돌이 발생하지 않는다. 완료된 레이드 소요 시간: 93·154·191·191초.
   - 의미: 격돌 동결의 핵심은 "제한시간"이 아니라 **보스 일반 공격·패턴 타이머 정지**다. 성공 시 10/16초 공격 봉쇄와 실패 시 방벽 20% 피해가 밸런스에 미치는 영향이 본문 예상보다 크다.
2. **편린 속성 대미지 V1(10-17 패치)은 운영 DB에 적용되지 않았다.** 공격식에 속성 배율이 없고 `snapshot_element_multiplier_bp` 칸도 없다(화면은 값이 없으면 1.0으로 처리). 격돌 패치와 속성 패치는 **같은 공격식 한 줄을 문자열로 찾아 바꾸므로**, 나중에 적용되는 쪽은 원본 불일치로 중단된다. **어느 것을 먼저 적용할지 사용자 결정 필요**(R2-4).
3. **DOT·REGEN 틱은 `(현재시각 − run.started_at)`으로 "밀린 횟수"를 계산**한다. 동결 중 `started_at`을 옮기지 않으면 격돌이 끝나는 순간 밀린 DOT 피해·REGEN 회복이 한꺼번에 적용된다 → R2-2b의 공용 시각 이동 헬퍼 필수. 동시에 활성 패턴은 1개(`active_pattern_run_id`)뿐이다.
4. **공격 피해식(운영본):** `공명력 × 계수 × 난수 × hit_zone 배율 × 패턴 배율 × (광폭화 × 그로기) × 치명타`. 기존 `WEAK_POINT`는 약점 밖 타격에 `body_multiplier`(기본 1)를 쓴다. 격돌 버프 중 계산은 다음으로 고정한다.
   ```text
   weakFactor   = 격돌 약점 영역 안이면 2.0
                  (그 밖에서 기존 WEAK_POINT 영역 안이면 그 배율, 아니면 body_multiplier 또는 1.0)
   clashFactor  = weakFactor + clashComponent            (3.0 대성공 / 1.5 성공)
   legacyFactor = 기존 패턴 배율 × 그로기 배율
   finalFactor  = GREATEST(clashFactor, legacyFactor)
   피해 = 공명력 × 계수 × 난수 × hit_zone 배율 × finalFactor × 광폭화 배율 × 치명타
   ```
   학생 화면 `RaidBattlePage.tsx`의 피해 숫자 미리 계산도 같은 식으로 바꾼다.
5. **중계 실시간 알림:** `raid_combat_events` INSERT 트리거(`raid_emit_combat_broadcast_feedback`)가 정해진 이벤트 이름과 `*_SUCCESS`·`*_FAILED`만 `raid_broadcast_feedback`으로 넘긴다. `CLASH_STARTED`·`CLASH_SELECTED`·`CLASH_NOTE_JUDGED`·`CLASH_RESUMED` 등은 목록에 추가해야 중계 화면이 즉시 받는다. `raid_broadcast_feedback`은 **교사만 읽을 수 있다**(RLS) → 학생 화면은 폴링으로만 격돌 상태를 받는다.
6. **학생 화면 갱신 주기:** 상태 조회 1.9초(빠른 길 목록에 없음 → 2칸 대기줄 뒤에서 기다릴 수 있음), 틱 1.8~2.5초. 대책: 격돌 RPC 3개(지원·준비 완료·입력)를 `client.ts` 빠른 길 목록에 추가, 격돌 단계 중에만 상태 조회 간격 단축(권장 0.7초), 지원 마감은 화면에 5초를 보여주되 서버는 마감 후 약 2초까지 받아준다(유예).
7. **탭 대기열:** `useRaidTapBatcher`는 꺼질 때 대기열(최대 약 3초 분량)과 재시도 묶음을 지우지 않는다 → 격돌 종료 후 격돌 이전 탭이 버프 배율로 들어갈 수 있다. **격돌 시작 시 대기열·재시도 묶음을 비우는 처리**를 추가한다. 서버 공격 토큰은 3초 분량에서 멈추므로 재개 후 폭주는 없다.
8. **카메라 연출(10-20·21 추가):** `RaidCameraRig`·`RaidCinematicFxLayer`가 보스 화면을 흔든다. 격돌 고리는 카메라 층 **바깥**에 두고, 격돌 중에는 흔들림을 멈춘다.
9. **교사 일시정지 중첩:** `teacher_pause_raid`는 ACTIVE에서만 가능하고, 재개 시 정지 길이만큼 이동한다. 격돌 동결과 겹치면 같은 구간이 두 번 이동될 수 있다 → **권장 기본값: 격돌 진행 중(약 30초)에는 교사 일시정지를 막고 안내 문구를 띄운다**(R2-4).
10. **오디오:** 중계 오디오는 URL이 없으면 합성음으로 대체한다 → 격돌 효과음은 V1에서 DB 칸 추가 없이 합성음으로 운영. 오디오 프로필은 효과음마다 고정 칸이라, 사용자 지정 효과음은 V2에서 칸을 추가한다.
11. 기본 보스 프리셋의 `HP_RATIO` 패턴은 20%·18% 광폭화뿐이라 50% 격돌과 겹치지 않는다. 최근 레이드에도 HP 45~55% 패턴은 없다.

### R2-3. V1 구현 범위 (축소 확정, 본문 9.1·9.4 대체)

**서버**
- 새 테이블 3개:

  - 학생 `student_volunteer_raid_clash`, `student_ready_raid_clash`, `student_submit_raid_clash_input`

- 연습·미리보기는 **화면만으로** 동작(서버 호출 없음, 실전 무영향).

**V1에서 제외**

### R2-5. 구현 반영 (2026-10-28 r3)

- R2-4의 두 항목은 확정: **속성 대미지 V1을 운영에 먼저 적용 완료**, **격돌 진행 중 교사 일시정지 차단**.
- 격돌 설정은 R2-3의 `raid_combat_configs.metadata.clash` 대신 **별도 표 `raid_clash_configs`** 에 둔다. 이유: 운영 `teacher_save_raid_combat_config`가 화면이 보낸 `metadata`로 통째 덮어써서, 오래된 화면에서 전투 기믹을 저장하면 격돌 설정이 지워질 수 있다. → 새 표 4개(설정·세션·지원자·입력), 교사 RPC 3개(조회·저장·강제 종료).
- 판정: 화면에서 BAD 창 밖(너무 이른) 입력은 무시한다. 틀린 키·늦은 무입력은 MISS. 연타해도 가장 이른 인정 입력은 BAD라 이득이 없다.
- 복제(`teacher_clone_raid`)한 레이드는 격돌 설정을 복사하지 않는다(기본 OFF). 필요하면 복제 후 다시 켠다.
- 일시정지 중 남은 격돌 버프·봉쇄 시간은 재개 시 함께 밀린다(이미 끝난 버프는 되살리지 않음).
- 교사 테스트 도구(⚔ 격돌 설정 탭):
  - **🎬 격돌 리허설**: 실제 학생 오버레이(`RaidClashOverlay`)와 중계 오버레이를 그대로 띄우고, 브라우저 안의 가상 서버가 모집→추첨→판정→결과를 진행한다. 가상 지원자 수·가상 대표 결과(무작위/대성공/성공/실패)·학생/중계/둘 다 화면 선택. DB 기록 없음. `RaidClashOverlay`에 선택 prop `actions`를 추가해 서버 RPC 대신 가상 서버를 넘긴다(생략 시 기존과 동일하게 실제 RPC).
  - **🧪 지금 격돌 발동**: 교사 RPC `teacher_trigger_raid_clash` — ACTIVE 레이드에서 HP와 관계없이 즉시 발동(레이드당 1회, 50% 발동과 같은 세션 사용, HP는 바꾸지 않음, `CLASH_MANUAL_TRIGGER` 이벤트 기록). 실제 효과·페널티가 적용되므로 테스트용 레이드에서 사용.
  - 격돌 키 입력은 글자 입력칸에 타이핑 중일 때 가로채지 않고, 연습 모드는 8개 판정이 끝나면 키 입력을 놓아 준다.

## 0. 개발자에게 가장 먼저 전달할 사항

1. **이 문서는 구현 요청용이다. 격돌은 아직 구현되지 않았다.** 현재 공개 `main` 경로 및 운영 DB 조사에서 격돌 전용 테이블이나 CLASH 패턴 타입이 확인되지 않았다.
2. **기존 레이드, 공격·공명방벽·보스 패턴·약점 노출·전리품·보상 시스템은 보호한다.** 특히 기존 레이드 전리품 코드는 현재 저장소에 이미 존재한다. 격돌 작업으로 이를 지우거나 이전 버전으로 되돌리지 말 것.
3. **합의된 게임 규칙과 미확정 구현 제안을 혼동하지 말 것.** 본문에 `✅ 확정`, `🧪 초기 테스트안`, `⚙ 구현 권장`, `❓ 최종 확인 필요`를 명시한다. 사용자가 실제 적용값으로 승인한 수치는 변경하지 말 것.
4. **실제 SQL/TSX 소스를 읽고 신규 통합 패치를 만들어야 한다.** 본 문서의 파일·함수명은 현재 조사로 확인되지만, Claude가 작업하는 시점의 `main`과 DB는 다시 확인한다.
5. **서버를 권위(authoritative source)로 삼는다.** 사용자 화면의 타이머·애니메이션은 로컬 렌더링하되, 지원자, 선정자, 입력 유효성, 점수, 버프·페널티, 전투 재개는 서버가 일원화한다.
6. **단순히 `raids.status='PAUSED'`로 변경해서 격돌을 구현하지 않는다.** 기존 PAUSED는 교사 수동 일시정지 및 타임라인 변경을 담당한다. 격돌에는 별도의 전투-잠금/단계 상태가 필요하다. 기존 일시정지와 공존하도록 설계할 것.
7. 기존 코드를 변경하기 전에 소스 백업, 기능 플래그(레이드별 `clash_enabled=false` 기본), 회귀 테스트를 준비하고 단계적으로 배포한다. 아직 사용자는 이 문서에서 **운영 DB 변경이나 GitHub 커밋을 요청하지 않았다.**

## 1. 게임 디자인 의도와 핵심 경험

- 레이드 이상적인 **실제 전투 진행 시간은 180~200초**를 목표로 한다. 격돌을 별도의 극적인 순간으로 삽입한다.
- 격돌은 **학생 1명이 도전하고 나머지 모험가 전원이 응원하는 길드 이벤트**다. 모든 학생이 동시에 QTE를 수행하지 않는다.
- 격돌 도중 학생은 보스에게 피해를 입힐 수 없고 **보스도 공격하지 않는다.** 일반 공격·보스 공격·기존 보스 패턴 타이머가 안전하게 정지한다.
- 한 학생의 빠른 판단, 리듬감, 타이밍 능력으로 모든 학생에게 유리한 10초간의 집중 화력 기회를 제공한다.
- 입력 UI는 로스트아크 격돌처럼 **고정된 파란색 원형 판정 고리 + 바깥에서 안쪽으로 수축하는 고리 + 중앙 키 입력 지시**로 만든다. **수평 이동 판정선 UI는 사용하지 않는다.**
- 결과마다 색상·타격감이 명확해야 한다. `PERFECT` 황금색, `GOOD` 파란색, `BAD` 빨간색. `MISS`는 별도 실패 표시.
- 실시간 영상 송출은 하지 않는다. **서버의 공통 시각·시퀀스·작은 판정 이벤트만 배포**하고 학생·중계 클라이언트가 같은 고리 연출을 렌더링한다.
- **난이도 쉬움·보통·어려움을 모두 V1에 구현**한다. 초기에 쉬움으로 운영한 뒤 익숙해지면 어려움 격돌을 가진 후반 보스를 설정할 수 있어야 한다.

### 2.1 3단계 결과의 기대 경험

- **대성공(13~16):** 한 학생이 보스를 완전히 제압. 길드 전체 10초 공격 찬스, 16초 안전 시간. 큰 황금 연출.
- **성공(8~12):** 보스의 공격 저지. 10초 약점과 중간 수준 추가 화력, 10초 안전 시간. 푸른 연출.
- **실패(0~7 또는 무지원):** 보스의 강력한 반격으로 남은 공명방벽의 20% 피해. 붉은 충격 연출. 실패해도 학생을 조롱하거나 낙인찍는 UI는 만들지 않는다.

### 2.2 보스 HP 50% 판정

**정상 이벤트 조건:** 변경 전 `current_hp / max_hp > 0.50`, 변경 후 `current_hp / max_hp <= 0.50`, 그리고 그 레이드에 아직 격돌 시도가 없는 경우. 정확히 50.00%가 되는 공격도 발동한다.

- 공격 배치 안의 여러 타격이 한꺼번에 50%를 넘길 수 있으므로 **실제 서버 HP 갱신 트랜잭션에서 원자적으로 1회** 감지한다.
- `raid_clash_sessions(raid_id)` UNIQUE 등으로 재발동을 원천 봉쇄한다.
- **제안:** 단발 피해로 보스 HP가 50% 위에서 곧바로 0이 되어 토벌된 경우에는 토벌 종료를 우선하고 격돌은 건너뛴다(❓ 세부 예외 최종 확인 필요). 일반 상황에서 클라이언트 렌더링만으로 50% 발동을 결정하면 안 된다.
- **제안:** 50%에 도달했을 때 다른 특수 패턴이 실행 중이면, 해당 패턴 타이머를 정지시켜 격돌을 우선 진행하고 이후 정확히 이어서 진행한다(❓ 우선순위 정책 확인 필요). 패턴을 실패 처리하거나 소실시키면 안 된다.

## 3. 원형 수축 고리 QTE — 화면·입력 명세

### 3.1 시각 구성 ✅

참고 이미지 2장(별도 압축 패키지에 포함):

- `references/lostark_clash_reference_1.png`: 여러 입력 고리가 화면 위에 분산되고 타이밍 판정이 발생하는 사례.
- `references/lostark_clash_reference_2.png`: 키(`W`, `R`, `E` 등)가 내부에 쓰인 파란 수축 고리의 자세한 형태.

**한 입력 고리의 표시 요소:**

1. 반투명 청색의 고정 원형 판정 테두리(target ring).
2. 그보다 큰 반경에서 시작해 시간이 흐르며 **동심원 형태로 줄어드는 청색 링(shrinking ring)**.
3. 중앙에 현재 눌러야 할 글자/버튼(PC 키 또는 모바일 터치 표시).
4. 움직이는 링과 고정 링이 일치하는 순간 입력하면 `PERFECT`, 근처는 `GOOD`, 멀면 `BAD`, 잘못 누르거나 제한 시간 경과는 `MISS` 또는 사전 정의한 오입력 처리.
5. 판정 순간 해당 고리는 색상 섬광과 SFX 출력 후 소멸, 다음 노트 진행.
6. 8회 누적 진행도(`4/8`), 현재 점수, 최종 결과를 명확하게 표기한다.

**판정 결과 색상 확정:**

| 판정 | 색상 | 표현 | 점수 |
|---|---|---|---|
| PERFECT | 황금 / 밝은 금빛 | 황금 테두리, 강한 링 파열과 광채 | 2 |
| GOOD | 푸른빛 | 푸른 파동, 간결한 긍정 효과 | 1 |
| BAD | 붉은빛 | 붉은 충격·작은 떨림 | 0 |
| MISS | 회색 또는 어두운 붉은빛(제안) | 미입력/오입력 안내, 다음 노트로 진행 | 0 |

**구현 기준:** SVG 또는 CSS transform/opacity 기반. UI 60fps 애니메이션은 클라이언트에서 수행하지만 **60fps 서버 송신은 금지**한다. 프레임이 떨어져도 절대 시간 기준으로 수축 위치와 판정을 계산한다. 가로로 움직이는 게이지/선은 최종 UI로 쓰지 않는다.

### 3.2 키 입력·터치 접근성 ⚙ / ❓

> **r2:** 이 절은 R2-1로 대체. PC·크롬북 전용, Q/W/E/R 무작위, `event.code` 판별, 터치·클릭 입력 불가.

- PC: `Q/W/E/R`와 같은 키를 중앙에 표시하는 설계가 이전에 제안되었지만, **최종 사용할 키 배치는 아직 확정되지 않았다**. Claude는 **키 세트를 데이터로 변경 가능하게 구현**하고 `QWER`를 잠정 기본 세트로 두는 방안을 추천한다.
- 모바일: 각 원형 고리를 터치 또는 화면에 나타나는 동일 레이블 버튼으로 누를 수 있게 한다. 스마트폰에서 실제 물리 키보드를 강제하지 않는다.
- 화면 터치/마우스 클릭이 일반 보스 공격으로 전달되지 않도록 격돌 오버레이가 포인터·키 이벤트를 캡처한다.
- 키 반복 입력(`event.repeat`)과 한 노트에 대한 연타는 중복 집계 금지.
- 격돌 이외의 일반 게임 UI/브라우저 동작에 영향을 주지 않도록 핸들러 등록·해제 정확히 처리.
- 화려한 움직임이 힘든 학생을 위해 `prefers-reduced-motion`에서는 배경 이펙트를 줄이되 **판정 타이밍 자체는 동일**하게 유지한다.
- 화면 복구/재접속 시 이미 판정된 노트는 서버 기록을 불러오고 남은 시퀀스를 진행한다.

### 3.3 노트 구성과 패턴 배치 ⚙ / ❓

- **8개 입력**은 고정. 패턴의 수축 속도·고리 크기·위치·수축 목표 시각은 난이도 프로필에 따름.
- 여러 고리를 미리 보여주는 시각 연출은 허용하지만, **V1 구현 권장안은 입력 순서가 명확한 순차 노트**다. 동시에 복수 키를 눌러야 하는 구조는 최초 버전에서는 피하고 향후 도전형으로 확장 가능하게 설계한다.
- 사용자 참고 이미지처럼 화면 여러 위치에 고리를 분산해 등장시키되, 학생 시선이 이동할 시간을 충분히 제공하고 작은 모바일에서도 입력 가능한 크기를 확보한다.
- 노트 시작 전 3-2-1 준비 카운트와 참가자 이름·장착 캐릭터 화면을 권장한다(연출 시간은 플레이 테스트로 조절).
- 한 노트의 타이밍 구간이 완료되면 MISS로 확정하고, 전체 진행은 서버 제한시간에 따라 자동 종료된다.

## 4. 쉬움·보통·어려움 난이도 — 세 가지 모두 V1 구현 ✅

### 4.1 확정 원칙

- 레이드 초안의 격돌 설정에서 **EASY / NORMAL / HARD 중 한 가지** 선택한다.
- 같은 레이드의 격돌 8회 입력에 동일 프로필을 적용한다(동적 가속은 별도 옵션으로 미래 확장).
- 난이도는 **고리 수축 시간과 입력 허용 오차**로 구분하며, 점수·성공 기준·전투 효과는 난이도와 무관하게 동일하다.
- 격돌 시작 시 해당 레이드의 난이도 수치를 세션 스냅샷에 저장한다. 전투 중 설정을 바꿔도 진행 중인 격돌에 영향 없음.
- 교사 설정 화면에서 난이도별 **연습/미리보기**를 바로 시작할 수 있게 만든다. 연습은 운영 공격·공명방벽·보상에 영향이 없어야 한다.

### 4.2 🧪 초기 플레이 테스트용 권장 프리셋(미확정)

아래 수치는 앞선 대화에서 사용한 **실험용 제안치**이지 사용자 확정값이 아니다. `1.60초` 등은 한 고리가 외곽에서 이상적인 일치 시점까지 수축하는 목표 시간의 예시이며, 실제 애니메이션·노트 간격·디바이스 지연에 맞춰 조절할 것.

| 난이도 | 수축 시작→최적 타이밍 | PERFECT | GOOD | BAD | MISS |
|---|---:|---:|---:|---:|---|
| EASY | 1,600ms | 이상점 ±100ms | ±230ms | ±360ms | 바깥/미입력 |
| NORMAL | 1,300ms | ±80ms | ±180ms | ±300ms | 바깥/미입력 |
| HARD | 1,050ms | ±55ms | ±125ms | ±230ms | 바깥/미입력 |

**구간은 서로 배타적으로 판단:**

```ts
function judge(offsetMs: number, profile: TimingProfile): 'PERFECT'|'GOOD'|'BAD'|'MISS' {
  const error = Math.abs(offsetMs);
  if (error <= profile.perfectWindowMs) return 'PERFECT';
  if (error <= profile.goodWindowMs)    return 'GOOD';
  if (error <= profile.badWindowMs)     return 'BAD';
  return 'MISS';
}
```

- `offsetMs = 실제 인정 입력 시간 - 서버가 확정한 해당 노트의 idealHitAt`. 0ms가 정확한 원 일치 시각.
- 프리셋 값은 데이터로 분리한다. `if EASY else ...` 하드코딩 대신 설정/상수에서 구성한다.
- 판정 결과가 어렵게 느껴지면 **HARD까지 구현은 하되 운영 기본 난이도는 EASY로 시작**하는 것을 권장한다.
- `RaidPatternGenerator`의 기존 `EASY/NORMAL/HARD/EXTREME`는 **일반 패턴 생성 난이도**이며, **격돌 난이도 EASY/NORMAL/HARD와 별개**다. 서로 영향을 주거나 기존 EXTREME 옵션을 삭제하지 말 것.

### 4.3 권장 플레이 테스트 방법

1. 교사 운영 패널에서 난이도별 독립 연습 모드를 제공하고, 테스트 학생 최소 3~5명이 PC와 모바일에서 각각 3회 이상 수행.
2. 8타 점수, 노트별 `PERFECT/GOOD/BAD/MISS`, 기기·브라우저, 네트워크 RTT, 누른 시각 오차를 **테스트 로그**로만 수집. 성적/평판으로 사용하지 않음.
3. EASY에서 대부분이 일정 횟수 연습 후 `8점`을 넘길 수 있는지, HARD가 숙련자에게 도전적인지 관찰.
4. 고리 UI가 과도하게 빠르거나 원이 명확히 겹쳐 보이지 않는 문제가 있으면 **판정 폭보다 애니메이션 가독성을 먼저 수정**.
5. 미리보기의 입력 판정은 실제 서버 판정 공식과 **동일한 공용 코어**를 사용해 결과 괴리가 없게 한다.

## 5. 지원자 모집과 대표 선발 — 5초 ✅

### 5.1 흐름

1. HP 50% 조건 감지와 동시에 격돌 세션을 생성하고 전투 전체를 동결한다.
2. `VOLUNTEERING` 상태로 **5초** 동안 참가 가능한 학생에게 `⚔ 격돌 지원` 버튼 표시.
3. 누르면 `참가 신청 완료` 표시; 같은 학생의 중복 클릭은 1건으로 처리.
4. 지원 종료 시점까지 기록된 **유효 지원자 중 균등 무작위**로 1명을 서버가 선정.
5. 결과와 이름·캐릭터 이미지를 학생 화면 및 중계에 공개한 다음 QTE 시작.
6. 지원자가 **0명**이면 대표 선발/8회 QTE를 건너뛰고 즉시 `FAILED` 효과로 진행.

### 5.2 선발 원칙과 자격

- **확정:** 기여도·공명력·순위는 격돌 대표 추첨 확률에 영향을 주지 않는다. 지원자라면 같은 기회.
- **구현 권장:** 해당 레이드에서 유효하게 참가한 `raid_participants` 학생만 지원 가능; 테스트 계정은 레이드 `include_test_accounts` 정책에 따름.
- **구현 권장:** 최초 지원 취소 기능은 생략하거나 명확한 `취소 후 재지원` 처리. 현재 게임 규칙에는 지원 취소 여부가 정해져 있지 않음.
- 지원 대상·선발 대상·실제 입력 권한은 **학생 인증과 `participant_id`를 서버에서 검증**한다. 학생이 다른 참가자 ID를 보내서 신청하거나 대신 입력할 수 없어야 한다.
- 추첨 결과는 서버에 저장하고 중계에서 연출용 이름 셔플을 하더라도 **실제 무작위 선발을 브라우저에서 다시 하지 않는다**.
- 응원하는 나머지 학생은 조작 가능한 격돌 키보드 UI 대신 응원용 관람 상태를 본다.

### 5.3 5초 타이머의 권위

- 지원 마감은 서버 `volunteer_closes_at`의 절대시각으로 고정. 브라우저 타이머 숫자가 아닌 서버 기록 기준.
- 네트워크 요청이 마감 뒤 도착했다면 자동 거절하고, 이미 수락된 신청은 유효.
- 지원 완료 직전 동시에 여러 요청이 와도 같은 세션과 같은 모집 마감/응모자 명단을 바탕으로 1인만 선정한다.

## 6. 격돌 중 전투 정지와 재개 — 서버 보장 ✅

### 6.1 정지해야 하는 것

- 학생 전체의 보스 일반 공격 및 특수 패턴용 타격 처리.
- 보스 일반 공격 및 피해 처리.
- 기존 일반 패턴의 작동 시계 및 만료(무력화, 약점, DOT, 필살기, 광폭화/그로기 등의 시간제 타이머를 운영 방침에 맞게 정확히 정지).
- 전투 제한 시간/남은 시간 카운트(`raids.starts_at`, `ends_at`)의 실효 진행.
- 전투 중 예상 DPS·화력 검증 등의 시간 기반 진도.

### 6.2 동결 구현 전략 ⚙

**권장:** `raids.status`는 `ACTIVE` 그대로 두고, 별도의 서버 전투 잠금 상태를 둔다. 예: `raid_clash_sessions.phase IN ('VOLUNTEERING','SELECTED','COUNTDOWN','PLAYING','RESOLVING')`일 때 `combat_frozen=true`. 또는 `raid_combat_states.clash_phase` 스냅샷을 유지해도 된다. 어느 쪽이든 서버 단일 진실원천은 명확히.

- `submit_raid_tap_batch`는 HP 50% 도달 즉시 격돌 시작 기록과 함께 정상 공격을 차단한다. 클라이언트가 늦게 동결 상태를 받더라도 서버가 가드한다.
- `raid_combat_tick`는 격돌 중 기존 보스 공격과 `raid_advance_patterns`를 실행하지 않는다. 대신 아주 가벼운 격돌 만료/상태 전환 검사만 수행한다.
- `raid_advance_patterns`, `raid_apply_barrier_damage` 등 우회 경로에서도 격돌 락을 검사해야 한다(격돌 종료의 명시적 실패 페널티 같은 예외는 신뢰 가능한 내부 경로로만 허용).
- 학생 공격 배치 큐가 격돌 시작 직전에 쌓여 있더라도, 격돌 중 받은 일반 타격은 **리플레이하지 않고 무효 처리**한다. 클라이언트의 임시 피해 숫자와 서버 HP가 어긋나지 않도록 신호를 준다.
- 격돌 전투 동결을 교사의 기존 일시정지와 충돌하지 않게 한다. 격돌 상태에서 교사가 `PAUSED`를 누른 경우 복귀 정책을 명시하고 이중 시간 이동을 방지한다.
- 브라우저가 꺼져도 세션 기록은 살아 있다. server-side lazy tick 또는 스케줄러가 다음 유효 요청에서 기한을 계산해 자동 종료하도록 한다.

### 6.3 재개 시각과 타이머 이동

- `clash_freeze_started_at`와 `combat_resumed_at`를 서버에서 확정한다.
- 일시정지된 벽시계 시간 Δ만큼 `raids.starts_at/ends_at`, 활성 `raid_pattern_runs.started_at/ends_at`, `raid_combat_states.next_boss_attack_at`, `groggy_until`, 기타 활성 DOT·타이머 기준 시각을 **한 번만** 앞으로 이동한다.
- 현재 `teacher_resume_raid`가 이동시키는 필드와 중복 적용되지 않게 공통 타임라인 이동 헬퍼로 분리하는 것을 강력 권장.
- 격돌 이후 적용되는 성공 효과의 **10초/16초는 전투가 재개된 순간부터** 시작한다. 모집 5초, QTE 8회, 연출 대기 때문에 성공 보너스가 줄어들어서는 안 된다.
- **대성공 보스 일반 공격 중단 16초:** 이 기간 일반 공격은 발생하지 않는다. 기한이 끝날 때까지 밀린 공격을 몰아서 수행해서는 안 된다. 첫 다음 공격은 일반 공격 스케줄 규칙을 따라 정상적으로 배치.
- **성공 보스 일반 공격 중단 10초:** 동일하되 10초.
- 실패에서는 별도 봉쇄 없이 기존 일반 공격 스케줄대로 재개; 실패 20% 공명방벽 피해는 정확히 1회만 적용한다.
- 기존 특수 패턴은 동결 종료 후 이어서 진행하되, 보스 일반 공격 봉쇄만으로 특수 패턴까지 10/16초 취소하는 것으로 해석하지 않는다. 격돌 재개와 겹치는 특수 패턴의 연출 타이밍은 조정 가능.

### 6.4 50% 타격 중 처리의 원자성

- **한 배치에 여러 타격**이 있는 경우, HP가 최초 50%를 통과하는 타격은 인정하고 그 시점에 격돌 락·세션을 확정한다. 같은 배치의 후속 타격이 추가 HP 감소를 일으키지 못하게 해야 한다.
- 다수 학생의 동시 공격 요청은 DB 직렬화/기존 잠금 게이트와 조합한다. `raid_attack_batches`의 기존 멱등성, 기여도 기록, 골드 정산에 영향을 주면 안 된다.
- 단순히 클라이언트가 HP=50% 상태를 봤을 때 `start_clash()`를 호출하는 방식은 레이스 조건과 중복 발동 위험 때문에 금지.

## 7. 결과·점수·대미지·공명방벽 규칙 ✅

### 7.1 점수 계산

```ts
const POINTS = { PERFECT: 2, GOOD: 1, BAD: 0, MISS: 0 } as const;
// 8노트 모두 서버 확정 후 합계
const totalScore = results.reduce((sum, j) => sum + POINTS[j], 0); // 0..16
const outcome = totalScore >= 13 ? 'GREAT_SUCCESS'
              : totalScore >= 8  ? 'SUCCESS'
              : 'FAILED';
```

- 모든 퍼펙트: 16점 대성공.
- 6회 퍼펙트+1회 굿+1회 미스: 13점 대성공.
- 4회 퍼펙트+4회 미스: 8점 성공.
- 3회 퍼펙트+1회 굿+4회 미스: 7점 실패.
- 미참여자 0명: 8회 QTE 생략, `FAILED`로 기록; 특정 학생의 점수 0으로 조작해 만들어내지 않음.

### 7.2 결과별 효과

| 결과 | 약점 노출 | 격돌 전용 피해 효과 | 보스 일반공격 봉쇄 | 방벽 페널티 |
|---|---|---|---|---|
| GREAT_SUCCESS 13~16 | **10초** | **10초, 추가 +200%** (유저 정의: 가산 성분 `3.0×`) | **16초** | 없음 |
| SUCCESS 8~12 | **10초** | **10초, 추가 +50%** (유저 정의: 가산 성분 `1.5×`) | **10초** | 없음 |
| FAILED 0~7 | 없음 | 없음 | 없음 | **현재 잔여 HP의 20%** |

### 7.3 가장 중요한 계산: 곱연산 금지, 완성된 배율의 **합연산** ✅

사용자가 명시적으로 정한 예시:

> 일반 공격은 100%(1.0배). 약점 타격 자체가 200%(2.0배)일 때, 격돌 대성공은 **약점 200% + 격돌 300% = 500%**, 즉 **5.0배**. 격돌 성공은 **약점 200% + 격돌 150% = 350%**, 즉 **3.5배**.

**절대 금지:** `weakMultiplier * clashMultiplier`로 `2×3=6배`, `2×1.5=3배`를 만드는 것. 사용자는 이것이 아니라 **2+3=5배 / 2+1.5=3.5배**를 원한다.

해석을 명시적으로 코드로 고정:

```ts
// Clashed buff during its 10-second active window:
// * great-success: clashComponent = 3.0
// * success:       clashComponent = 1.5
// * otherwise:     clashComponent = 0.0
// weakFactor = actual active weak-point hit multiplier (example 2.0),
//              or 1.0 for non-weak hit.
const combinedHitFactor = weakFactor + clashComponent;
// example: weak 2.0 + 3.0 => 5.0
// example: weak 2.0 + 1.5 => 3.5
```

**주의(수치 정의의 모호성):** '추가 대미지 +200%'라는 버프 명칭만 보면 `+2.0`처럼 보이지만, 사용자의 **명시적 실제 피해 예시에서는 '격돌 300%'라는 전체 성분**을 약점 200%에 더한다. **구현 검증의 우선 기준은 위의 5.0배·3.5배다.** 버프 툴팁/설정 필드도 혼동이 없도록 `great_clash_component_multiplier=3.0`, `success_clash_component_multiplier=1.5` 등의 이름 사용 권장.

✅ **r2 확정: 일반 부위 4.0배(대성공)/2.5배(성공) — B안. 그로기와는 큰 값만(R2-1, R2-2c-4).** 아래는 r1 원문.

~~❓~~ **약점이 아닌 일반 부위를 때렸을 때의 최종 배율은 유저가 직접 숫자로 예시를 들지 않았다.** 같은 가산식을 그대로 적용하면 대성공 `1+3=4배`, 성공 `1+1.5=2.5배`가 된다. 이 값은 **현재 수식에서 자연스럽게 도출되는 구현 권장안이며, 새 정책을 임의로 확정하지 말 것**. 최종 배포 전에 사용자 확인 가능하면 확인하되, 확인 전에는 문서상의 가정임을 유지한다.

**다른 일반 배율과의 관계:** 공명력, 난수 변동, 속성 보정, 치명타, 광폭화·그로기·기타 타격 배율은 기존 엔진의 규칙을 최대한 유지한다. `weakFactor + clashComponent`가 **한 번만** 적용되도록 기존 `v_pattern_multiplier`와 중복곱을 제거/분리한다. 만약 기존 WEAK_POINT 패턴도 동시에 남아 있으면 약점 보너스가 두 번 붙지 않게 처리한다.

### 7.4 격돌 약점 노출: 실제로 맞혀야 강해지는 약점

- 약점 노출 10초는 **보스의 약점 타격 영역을 10초간 눈에 띄게 보여준다**는 뜻. 보스 어디를 눌러도 자동으로 '약점 2배'가 되는 것으로 임의 변경하지 말 것.
- 현재 `WEAK_POINT` 패턴은 `x`, `y`, `width`, `height`, `multiplier`를 사용하여 화면 영역과 피해를 결정한다. **그 메커니즘을 활용/재사용**하되 CLASH 보너스가 기존 `raid_pattern_runs` 한 자리만 차지하는 설계에 종속되지 않게 한다.
- 권장: `clash_weak_until`, `clash_weak_zone`, `clash_component_multiplier`를 별도로 보관하고, 서버 공격 함수가 active weak zone을 검증한다.
- 기존 WEAK_POINT와 겹칠 때는 **약점 영역 우선순위·최대 배율 적용** 등 중복 방지 규칙을 코드에 명시. 2개의 WEAK_POINT를 단순 곱하거나 덧붙여 갑자기 10배 이상이 되는 오류를 막아야 한다.
- 약점 노출 타이머와 추가 대미지 타이머는 모두 10초지만 각각 독립적인 상태 필드로 유지하면 후속 변경이 편하다.

### 7.5 실패의 공명방벽 피해: **현재 잔여량 기준** ✅

**반드시:**

```ts
const before = currentBarrierHp;
const requestedDamage = Math.round(before * 0.20); // 정수 반올림 방식은 ⚙ 구현 권장
const after = Math.max(0, before - requestedDamage);
```

- 예: 실패 당시 남은 방벽 400,000 → 80,000 피해 → 320,000.
- 예: 최대 방벽 1,000,000, 현재 잔여량 100,000 → 20,000 피해. 최대 HP의 20%인 200,000 피해가 **아님**.
- 기존 `raid_apply_barrier_damage(p_barrier_ratio)`는 **최대 공명방벽 HP 기준 비율을 사용한다.** 그러므로 `p_barrier_ratio=0.20`으로 호출하면 **잘못 구현**된다.
- 구현 권장: `raid_apply_barrier_damage`에 넘기는 정확한 **고정 피해량**을 서버 트랜잭션에서 읽은 현재 HP의 20%로 산출하여 `p_fixed_damage=requestedDamage`, `p_barrier_ratio=0`으로 호출하거나 동등한 내부 함수를 사용. 방벽 HP read와 피해 적용의 잠금 순서를 검증.
- 20% 페널티는 격돌 실패 결과를 처음 확정할 때 단 **1회**. 새로고침·중복 RPC·중계 반복 재생으로 반복 적용 금지.
- 만약 격돌 시점에 방벽이 비활성/미초기화인 레이드라면 잘못된 함수 호출로 전체 전투가 죽지 않도록 명시적인 처리·경고 정책 필요(⚙ 보수적인 권장: 격돌 사용을 방벽 활성 레이드에서만 허용).

### 7.6 180~200초 전체 밸런스

- 10초 버프 구간은 목표 전투 180~200초의 약 5.0~5.6%.
- 하지만 5배 공격 구간은 시간 비중이 낮아도 **공격 집중 및 약점 적중률**에 따라 보스 HP가 크게 변할 수 있다. '무조건 밸런스 영향이 없다'고 단정하지 말 것.
- 교사의 기존 `RaidBalanceLabPage.tsx`, `raid_balance_reports`를 활용해 **격돌 미사용 / 성공 / 대성공** 세 시나리오의 예상 토벌 시간을 비교할 것을 권장한다.
- 목표 전투 180~200초는 격돌 이벤트 중 **동결된 시간 제외한 실제 전투 시간인지** UI에서 구별해 기록한다(권장: `active_combat_seconds`와 `wall_clock_seconds` 둘 다 기록).

실제 확인된 주요 함수:

- `public.submit_raid_tap_batch(bigint,uuid,jsonb)`: 공격 배치 처리, HP 감소, 배치 멱등성, 큰 전투 잠금. `raids.status='ACTIVE'` 확인.
- `public.raid_combat_tick(bigint)`: 서버 보스 일반공격 틱·패턴 진행. 현재 약 800ms 스로틀 / advisory lock.
- `public.raid_advance_patterns(bigint)`: 활성 패턴 만료, `HP_RATIO` 포함 패턴 트리거·이벤트 시작. 기존 pattern type/trigger와 충돌 방지.
- `public.raid_apply_barrier_damage(bigint,bigint,numeric,text,jsonb)`: 방벽 피해 적용, **비율은 최대 방벽 HP 기준**.
- `public.teacher_pause_raid(bigint)` 및 `public.teacher_resume_raid(bigint)`: 운영자 수동 정지/재개. resume 시 여러 타이머 날짜 이동.
- `public.get_raid_battle_state(bigint)`: 학생 전투 state/metadata JSON 응답.
- `public.teacher_get_raid_broadcast_state(bigint)`: 교사 중계 state/metadata JSON 응답.
- `public.raid_e3_finish_pattern_success(...)`: 기존 성공 시 그로기 적용. 격돌 약점 + 공격 방어 봉쇄와 동일하지 않으므로 무턱대고 재사용 금지.

### 8.3 치명적인 기존 엔진 제약

1. `submit_raid_tap_batch`는 단순 공격 함수가 아니라 600줄 이상 복합 전투 RPC. 단순 전체 파일 덮어쓰기가 아니라 **기존 정확한 소스와 변화를 검사한 후 최소 수정**할 것.
2. `raid_combat_tick`는 `raid_advance_patterns`를 실행하고 보스 공격 예약 시간을 확인한다. **겉으로 UI만 멈춰서는 타이머가 계속 흘러 강제 실패·보스 공격이 발생한다.**
3. `raid_advance_patterns`는 `raids.starts_at/ends_at` 및 `raid_pattern_runs.ends_at`에 직접 의존한다. 동결 동안 실행을 차단하고 재개할 때 시각을 옮겨야 한다.
4. `teacher_resume_raid`가 이미 `starts_at`, `ends_at`, `raid_pattern_runs.started_at/ends_at`, `next_boss_attack_at`, `groggy_until`을 이동한다. 격돌 동결 시간이 **2번 더해지거나 0번 더해지면 안 된다.**
5. `get_raid_battle_state`는 학생 본인 `me`와 전투 상태 JSON을 제공하고, 교사 중계는 독립 RPC를 사용하므로 **둘 다 격돌 상태를 같은 스키마로 제공**해야 한다.
6. `RaidBattlePage.tsx`에서 약점 UI는 현재 `active_pattern.pattern_type === 'WEAK_POINT'`일 때만 그린다. CLASH 약점은 별도 활성 필드를 읽도록 만들어야 기존 패턴을 덮어쓰지 않는다.
7. 학생 전투 UI는 여러 클라이언트에서 `raid_combat_tick`을 대략 1.8~2.5초 간격으로 호출한다. **클라이언트 하나가 안 열려도 상태 전환이 진행될 전략** 필요. Realtime 알림은 성능 최적화, 폴링/서버 틱은 복구 장치.

| `raid_clash_inputs` | 서버가 확정한 `session_id + note_index UNIQUE`, 입력/서버 수신 시각, 판정, 획득 점수, 예상 키, 요청 ID, 인증된 참가자 |
| `raid_clash_events` 또는 기존 `raid_combat_events` | 모집 시작, 지원자 선정, 각 노트 판정, 결과, 효과 발동, 전투 재개를 감사 가능하게 저장 |

**운영상 고려:** `raid_clash_configs`를 별도 테이블로 둘지 `raid_combat_configs.metadata.clash`로 둘지는 기존 앱 설계와 마이그레이션 충돌을 보고 결정할 수 있다. 단 **설정 검증과 버전 관리, 교사 권한, 설정 동결**은 유지.

### 9.2 권장 상태 머신

```text
DISABLED / NOT_TRIGGERED
          |
          | HP first crosses 50%, clash enabled
          v
VOLUNTEERING -- (5 seconds, no volunteers) --> RESOLVING:FAILED
          |
          | volunteers >= 1 / uniform random
          v
SELECTED -> COUNTDOWN -> PLAYING (8 input rings)
                         |
                         | 8 judged OR timeout
                         v
                     RESOLVING
                         |
                         | atomically effects + timeline resumption
                         v
                       FINISHED
```

- `VOLUNTEERING`, `SELECTED`, `COUNTDOWN`, `PLAYING`, `RESOLVING` 전체가 전투 동결 상태.
- `FINISHED`에서만 공격 재개. 이미 FINISHED면 `resolve` 재호출은 **아무것도 재지급/재적용하지 않고 저장된 결과 반환**.
- `RAID_FAILED`/`RAID_COMPLETED` 전역 종결과 겹칠 때 충돌 방지 상태 전이 필요.
- 네트워크 절단·입력 기한 만료는 MISS 처리로 끝날 수 있어야 한다. 대기 상태가 무한히 지속되면 안 된다.

### 9.3 설정 저장·동결

- 기본 값 `enabled=false`: 기존 레이드의 결과 보존. 신규 레이드에 교사가 체크하면 활성화.
- 설정은 `DRAFT` / `LOBBY_OPEN`에서 수정 가능(현재 전투 설정 정책과 정합). ACTIVE 이후 읽기 전용.
- 세션 생성 순간 `config_snapshot`에 `difficulty`, `thresholds`, `note_schedule`, `volunteer_deadline`, 효과를 모두 복사한다.
- 트리거는 DB 인덱스/제약으로 단 한 번만; 중간에 브라우저 화면을 복제해도 세션을 새로 만들 수 없음.
- 타이머는 서버의 `clock_timestamp()`와 저장된 절대시각 사용. 새로고침/탭 전환 후에도 이어진다.

### 9.4 필수 RPC 후보 및 권한

> **r2:** V1 RPC는 R2-3(새 RPC 4개 + 내부 함수 1개)으로 확정. 아래 목록 중 상태 조회·미리보기 RPC는 만들지 않는다. 권한 원칙은 그대로 유지.

실제 함수명은 프로젝트 명명 규칙에 맞춰 조정 가능하지만 **역할별 분리**가 중요하다.

| RPC 제안 | 역할 | 핵심 기능 |
|---|---|---|
| `teacher_get_raid_clash_config` | 교사 | 현재 격돌 설정·미리보기 |
| `teacher_save_raid_clash_config` | 교사 | 난이도/ON-OFF 저장, 값 검증 |
| `student_get_raid_clash_state` | 참가 학생 | 본인 역할에 맞는 모집/대표/노트/결과 상태 조회 |
| `student_volunteer_for_raid_clash` | 해당 레이드 학생 | 5초 이내 지원, 중복 신청 방지 |
| `student_submit_raid_clash_input` | 선발 학생 **1명** | 정해진 노트의 입력, 한 번만 판정, 재시도 멱등성 |
| `raid_advance_clash` | 제한된 내부 경로 | 모집 마감, 추첨, QTE 타임아웃, 결과 효과, 재개 |
| `teacher_get_raid_clash_broadcast_state` 또는 기존 broadcast 확장 | 교사 | 실시간 공개 상태·판정·연출 데이터 |
| `teacher_preview_raid_clash` | 교사 (실행 중 운영 DB 변경 금지) | 독립 연습/미리보기 |
| `teacher_resolve_stuck_raid_clash`(옵션) | 교사+감사 로그 | 장애 시 명시적 종료/복구. 남용·재추첨 방지 |

- SECURITY DEFINER 함수를 사용할 때 **고정 `search_path`·명시적 권한 검증·인증 학생 매핑 검증**.
- `anon` 또는 다른 학생에게 `SELECT`로 지원자 목록/선발 비공개 노트·교사 제어 데이터가 새지 않도록 RLS / RPC projection 분리.
- RPC 호출 결과 타입에 `session_version`, `phase`, `server_now`를 넣고 **재시도·낡은 클라이언트 응답의 역전** 방지.
- `raid_advance_clash`는 DB 잠금이 단일 레이드 결과를 직렬화해야 한다. 동시에 호출되어도 정확히 하나의 선발과 하나의 최종 결과만 발생.

### 9.5 판정 권위와 네트워크 지연 ⚙

> **r2:** 학생 화면 기준 판정 + 서버 타당성 검사로 확정(R2-1). 아래는 r1 원문.

- 고리 프레임은 학생의 로컬 `requestAnimationFrame`으로 계산한다.
- 서버는 미리 정해진 각 노트 `ideal_hit_at`과 허용창을 안다. 학생은 해당 노트·키·시각 증거를 제출한다.
- **클라이언트가 전송한 'PERFECT' 같은 판정 문자열을 그대로 믿지 않는다.** 서버가 offset과 키/노트 일치를 확인해 점수 확정.
- 네트워크 지연이 있는 웹 환경에서 `server_received_at`만으로 55ms 하드 창을 적용하면 부당한 실패가 늘 수 있다. **서버 시각 보정, 측정 RTT, 시간 증거 검증과 허용 드리프트**를 설계한 뒤 테스트해야 한다. 반대로 조작 가능한 클라이언트 타임스탬프만 신뢰해도 안 된다.
- 보안과 공정성의 균형을 위해 첫 버전은 **서버가 정한 노트/시각 + 클라이언트의 단발 입력 이벤트 + 보수적인 지연 보정 검증**을 권장. 로컬 연출과 서버 점수가 불일치하면 authoritative 결과를 명확하게 동기화.
- 서버로 프레임 매번 전송 금지. 유효 QTE 8입력에 대해 최대 8건 수준의 판정 요청(+드문 재시도)이 목표.

## 10. 학생 UI 상세

### 10.1 비대표 학생 화면

1. 보스 HP 50% 도달: 화면 어둡게, 거대한 `⚔ 격돌 발생!` 문구와 긴장 효과.
2. 모두에게 5초 지원 패널/카운트. 지원 여부 명확히 표시.
3. 대표 확정 시 `길드의 대표 모험가: ○○○` 공개. 다른 학생은 QTE 입력 불가.
4. 대표 플레이 동안 고리·점수 등 핵심 연출을 **보기 전용**으로 재현하거나 `○○○ 격돌 중!` 응원 시각화.
5. `PERFECT / GOOD / BAD / MISS` 순간마다 적당한 강조. 타인에게 실패를 조롱하는 메시지 금지.
6. 결과 공개: `대성공! 10초간 약점 노출` 또는 `격돌 실패! 공명방벽 피해`. 종료 즉시 보스 타격 복구.

### 10.2 대표 학생 전용 조작 화면

- 선정 직후 집중을 위한 특별 화면 전환. 자신이 선발됨을 명확히 강조.
- 준비 카운트 후 원형 수축 고리 8개 진행. QWER/터치 패턴은 설정에서 주입.
- 지금 입력할 키/고리 영역은 터치 가능. 고정 파란 원 목표점과 외부 수축 링의 차이가 잘 보여야 함.
- 매 노트 즉시 황금/파랑/빨강 판정과 점수/누적 점수.
- 대표 학생이 브라우저를 새로고침하더라도 서버 기록을 읽어 남은 노트만 정확히 표시. 이전 판정 재입력 금지.
- 점수가 실패 확정 가능 상태라도 8회 진행을 정상 완료시키는지 여부는 연출 방침. **현재 대화에서 명시한 것은 8회**이므로 조기 종료를 임의로 추가하지 말 것.
- 네트워크 지연 중에는 서버 확인 중 표시를 제공하되 8개의 노트가 서로 엉키지 않도록 시퀀스 통제.

### 10.3 공격 입력 처리

- 학생이 화면을 클릭/탭해도 서버 격돌 락 상태에는 일반 보스 피해를 주면 안 됨.
- `useRaidTapBatcher`에 `enabled={!clashActive && ...}` 형태의 UI 가드를 추가하고 미전송 큐·진행 중 요청을 안전하게 처리.
- 클라이언트 자체 가드는 편의성일 뿐, **최종 서버 가드는 반드시 존재**.
- 버프 10초 시각이 사라질 때 배율 툴팁·공격 수치가 서버와 다르게 지속되지 않도록 시각 동기화.

## 11. 교사 16:9 중계 화면 / 방송 연출 상세

### 11.1 중계 상태 화면

1. **CLASH TRIGGER**: 보스 HP 50% 통과, 전투 BGM 감속/전환(가능할 경우), 크게 `격돌 개시`.
2. **VOLUNTEER**: 5초 카운트다운, 지원 인원 수와 기대감 연출.
3. **SELECTION**: 이름이 빠르게 흘러가는 연출 후 서버 선정자를 정확히 보여줌. 샘플 이름 랜덤 연출은 결과가 실제로 재추첨되는 것처럼 보이지 않게.
4. **COUNTDOWN**: 대표 학생 이름/길드/장착 편린, `3 2 1`.
5. **RING QTE**: 학생 화면과 같은 server `ideal_hit_at`·고리 위치·키, 진행도 `3/8`, PERFECT/GOOD/BAD/MISS 색상과 사운드.
6. **RESULT**: 대성공(금색), 성공(파랑), 실패(빨강) 등급과 최종 점수 표시.
7. **RESUME**: 보스 약점 보이기·피해 보정/공격 봉쇄 HUD → 원래 레이드 중계 UI 복귀.

> 핵심: **화면을 실시간 영상으로 스트리밍하지 않는다.** 학생과 중계는 동일한 서버 시계·판정 기록으로 로컬 렌더링한다.

### 11.2 레이아웃 가이드

- 16:9 중계 화면의 중앙은 보스와 수축 고리에 집중. 기존 참가자 좌우 레일은 어둡게 하거나 축소.
- 대표 이름, 대표 캐릭터/길드, 현재 `Q/W/E/R`(임시), `n/8`, 점수, 판정 결과만 크게. 수치 과다 금지.
- 푸른 링 위로 수축하는 원을 배치. PERFECT→황금 섬광, GOOD→파란 물결, BAD→붉은 충격.
- 주요 레이드 디스플레이(보스 HP·방벽 등) 일부는 얇게 유지할 수 있지만 **중앙 판정 고리의 가독성을 최우선**.
- 링 애니메이션은 클라이언트 `performance.now()`/서버 시계 보정으로 부드럽게 그리되, 판정은 서버 이벤트가 최종 권위.
- 가로 막대 판정선, 일반 슬라이더를 최종 격돌 UI로 도입하지 않는다.

### 11.3 오디오와 기존 기능 충돌 방지

- 기존 `RaidBroadcastAudioEngine`의 BGM/SFX 믹서, 음소거, 효과음 폴백(합성음), 성공/실패 BGM은 유지.
- 격돌 전용 큐 제안: `CLASH_START`, `CLASH_VOLUNTEER_END`, `CLASH_RING_READY`, `CLASH_PERFECT`, `CLASH_GOOD`, `CLASH_BAD`, `CLASH_MISS`, `CLASH_SUCCESS`, `CLASH_GREAT_SUCCESS`, `CLASH_FAILED`.
- SFX는 추가 오디오 URL이 없더라도 기본 폴백으로 동작. URL 미설정이 렌더링 무한로딩 원인이 되면 안 됨.
- 현재 이미 구현된 토벌 성공 후 **레이드 전리품 획득식 레이어와 공존**. 격돌은 전투 도중, 전리품은 토벌 후; 화면/오디오 상태 전이를 분리.
- 교사 전체 화면 및 사운드 활성화 버튼 유지. 브라우저 음향 자동재생 제한을 위반하지 않도록 유저 액션 기반 unlock 사용.

## 12. 교사 설정 패널 / 운영 도구

### 12.1 위치

현재 `src/features/teacher/raid/RaidV15ConfigPanel.tsx`의 `레이드 구성` 탭은 `COMBAT / PATTERNS / AUDIO / LOOT`가 있다.

**권장:** 기존 패턴 에디터에 격돌 설정 카드로 묻어두지 말고, 이 영역에 **`⚔ 격돌 설정` 독립 탭**을 추가. 기존 탭은 모두 유지.

### 12.2 필수 설정 필드

- `격돌 사용` ON/OFF (기본 OFF)
- `발동 보스 HP` 50%(V1 고정, 미래 확장 가능 구조)
- `모집 시간` 5초(V1 고정)
- `8회 입력`(V1 고정)
- `난이도`: EASY / NORMAL / HARD 드롭다운.
- 해당 난이도 프로필의 수축 시간, PERFECT/GOOD/BAD 오차: 테스트 모드에서는 조절 가능하게, 실전 적용은 버전 스냅샷 저장.
- `테스트/미리보기`: 학생 대표 QTE 데모와 교사 중계 미리보기를 실전 재화·보스 HP 무변경으로 실행.
- 결과 효과 카드: 대성공/성공/실패의 수치 **읽기 전용 표시**(초기 버전에서 현재 사용자 확정값 고정).
- `정지·재개 정상 여부`, `설정 검증`, `연결 상태` 표시 등 운영 안전장치.

### 12.3 운영 화면에서 고려할 일

- 격돌 없이 과거 레이드를 조회할 경우 관련 컴포넌트는 정상적으로 숨김.
- DRAFT·LOBBY_OPEN에서 편집 가능. ACTIVE 이후 세션 난이도 변경 불가.
- 신규 레이드 복제 시 CLASH 사용 여부·난이도 설정 복사 여부를 명확히 하고 기본값 정책 일관화.
- 기존 `RaidPatternGenerator`가 보스의 패턴을 생성/재생성해도 CLASH 설정이 사라지거나 중복 발생하지 않도록 보장.
- 학생 기기가 없다면 교사 미리보기에서만 독립 연습 가능; 운영 레이드에 접속한 학생에게 테스트 판정 이벤트를 뿌리지 말 것.

## 13. 비기능 요구사항: 성능, 보안, 일관성

### 13.1 서버 부하

- 대표 입력 8회만 서버 판정 요청. 나머지 학생은 state 조회/Realtime 수신만.
- 24명 이상 참가하는 기존 전투보다 요청량을 불필요하게 늘리지 말 것. 애니메이션 업데이트를 DB row update로 스트리밍 금지.
- 기존 `raid_combat_tick` 경합 가드와 호환. 격돌 도중 타격 트랜잭션이 DB row lock 대기열에 쌓이지 않게 반환.
- 중계/학생 응답에서 8개 노트 전체를 초당 여러 번 동일하게 내려보내기보다 **시퀀스와 서버 고정 시간**을 캐시/전송.
- 1분 이상 교사·학생이 재접속을 반복해도 타이머·판정 상태 회복.

### 13.2 신뢰성

- 모든 중요한 결과는 저장 후 브로드캐스트. UI 이벤트 수신이 유실돼도 서버 기록으로 복구.
- DB 유니크 제약으로 세션 1회, 지원 1회, 노트 1회, 보스 페널티 1회 강제.
- `session_version`과 확정 단계 순서를 사용해 늦게 도착한 응답으로 화면이 되감기지 않게 함.
- 무지원/불안정 통신/선발학생 종료/교사 이탈에도 종료 가능한 상태 머신.
- 사용자에게 공개한 점수/평가와 DB 점수 불일치 금지.
- `admin` RPC는 현재 교사 인증·학급 권한 확인 함수를 재사용하고, 학생이 교사 RPC를 호출하지 못하게 함.

### 13.3 접근성과 교실 운영

- 고리/키/점수는 색상만으로 표현하지 않고 `PERFECT / GOOD / BAD / MISS` 텍스트 병기.
- 모바일 작은 화면에서도 고리와 조작부가 충분히 큼.
- 실패 학생을 비난/낙인찍는 메시지나 강한 경고 SFX 반복 금지. 도전 자체가 길드에 기여한 것으로 묘사 가능.
- 실패해도 정해진 공명방벽 피해만 적용하고 과도한 추가 개인 페널티를 만들지 않는다.

## 15. 수용 테스트 매트릭스 — 반드시 통과

### 15.1 규칙·점수 테스트

- [ ] EASY/NORMAL/HARD가 모두 선택·저장·불러오기 가능.
- [ ] 세 난이도 모두 8회 입력, 점수·보상이 동일한 기준으로 판정.
- [ ] 판정 경계: `abs(offset)==perfectWindow`는 PERFECT, 그 초과·good 이하는 GOOD, 그 초과·bad 이하는 BAD, 그 외 MISS.
- [ ] 16점·13점 = 대성공, 12점·8점 = 성공, 7점·0점 = 실패.
- [ ] 네트워크 재시도로 노트 한 개에 2회 점수 지급하지 않음.
- [ ] 동일 키 자동반복/중복 탭으로 한 노트 2회 판정 불가.
- [ ] 부정확한 키·미입력·노트 인덱스 조작에 정확한 처리.

### 15.2 발동·지원·선발 테스트

- [ ] 보스 HP 50.01% → 50.00% 단발 첫 진입에서 시작.
- [ ] 보스 HP 50.01% → 49.99% 진입에서도 시작.
- [ ] 보스 HP 50% 아래서 지속 공격해도 2차 격돌 없음.
- [ ] 동시 여러 타격/중복 서버 틱에서도 세션 1개만 생성.
- [ ] 지원 0명: 5초 후 FAILED/방벽 20% 적용, 링 입력 없음.
- [ ] 지원 1명: 그 1명이 반드시 대표.
- [ ] 지원 N명: 유효 지원자에서 균등 무작위 1명.
- [ ] 지원 중복 클릭과 마감 직전 동시 RPC 경합에도 1명 1표.
- [ ] 교사/타 학생 계정으로 대표의 입력을 제출하면 차단.
- [ ] 다른 학생 계정으로 지원 신청을 위조하면 차단.

### 15.3 동결·타이머 테스트

- [ ] 격돌 동안 학생의 보스 HP 감소 0.
- [ ] 격돌 동안 보스 일반공격 발생 0.
- [ ] 격돌 동안 패턴 타이머 만료·DOT tick·예정된 일반공격 누적 발생 0.
- [ ] 격돌 도중 공격 배치가 늦게 도착해도 서버 HP가 줄지 않음.
- [ ] 재개 후 기존 활성 패턴 남은 시간이 격돌 전과 동일하게 유지.
- [ ] 재개 후 보스 일반공격이 10초/16초 봉쇄되고, 봉쇄 해제 뒤 누적 공격이 폭발하지 않음.
- [ ] 교사 수동 PAUSED/RESUME과 격돌 동결이 중첩되어도 시각 이동 한 번만 적용.
- [ ] 기존 HP_RATIO 패턴·TIME_SECONDS 패턴이 의도치 않게 중복 발동/소실되지 않음.
- [ ] 전체 전투 시간·벽시계 시간 지표가 구분되어 누적됨.

### 15.4 효과·피해 테스트

- [ ] 약점 배율 2.0인 약점 타격 + 대성공 성분 3.0 → **5.0배** (6.0배 아님).
- [ ] 약점 배율 2.0인 약점 타격 + 성공 성분 1.5 → **3.5배** (3.0배 아님).
- [ ] 약점/격돌 버프를 잘못 두 번 곱하거나 기존 그로기와 동일한 효과로 처리하지 않음.

- [ ] 대성공 16초/성공 10초 일반 공격 방지.
- [ ] 실패: 현재 방벽 400,000이면 **80,000** 감소. 최대 방벽 HP 기준이면 테스트 실패.

## 16. 장애 복구와 롤백

1. **기본 기능 플래그 OFF**: 마이그레이션 배포 후 기존 레이드는 변경이 없어야 한다.
2. `ACTIVE` 중 장애 시 진행 중 세션을 임의 초기화하여 **다른 대표를 재선발하지 않는다**. 타임아웃/미입력 정책으로 종료하거나 교사 전용 명시적 복구 RPC를 사용하고 감사 로그를 남긴다.
3. 서버 RPC를 교체할 때 기존 함수 정의·권한·시그니처 백업. 새 클라이언트가 구형 서버를 호출하면 안전하게 격돌 OFF로 표시되도록 배포 순서를 관리.
4. `raid_clash_*` 세션 및 입력 기록은 분석용으로 보존하고, 기능 OFF/코드 롤백은 상태 조회만 비활성화한다. 과거 레이드 결과와 골드 정산·전리품 기록은 손상되지 않아야 한다.
5. 이상 발생 시 `raid_combat_states`의 격돌 상태와 고정 시각을 진단. 기존 `PAUSED` 메타데이터·패턴 시간과 충돌하는지 검증 후 **정확히 한 번만** 재개 타임라인 보정.
6. 기존 프로젝트의 `npm install/ci`, 전체 빌드, Git push 등은 사용자 요청 및 저장소 운영 제약을 확인하고 수행한다. 사용자가 허락하기 전 임의로 운영 DB를 수정하지 않는다.

## 18. 미확정 사항과 구현에서 사용할 권장 기본 처리 — 반드시 구분

본 대화로 **명시적으로 확정된 사항은 2·4·5·7장의 ✅ 항목**이다. 그 외는 개발자에게 제시하는 좋은 기본값이며, 필요하면 사용자에게 묻는다.

| 항목 | 현재 합의 상태 | 구현 권장값 / 확인 포인트 |
|---|---|---|
| 3종 난이도의 정확한 ms 판정폭 | 🧪 미확정 | 4.2의 EASY/NORMAL/HARD 초기 프리셋으로 실제 기기 테스트 후 조정 |
| PC 입력 키 | ✅ r2 확정 | Q/W/E/R 무작위, `event.code` 판별, 키보드 전용 |
| 8개 고리 동시/순차 진행 | ❓ 미확정 | V1은 순차 입력, 여러 고리 시각적 예고 허용 |
| 격돌 직전 다른 특수 패턴의 우선순위 | ❓ 미확정 | 격돌 우선 → 활성 패턴 타이머 동결 → 재개 |
| 50%를 통과하면서 즉시 토벌한 경우 | ❓ 미확정 | 토벌 성공 우선, 격돌 건너뛰기 |
| 일반 부위 타격 시 격돌 추가 성분 | ✅ r2 확정 | 대성공 4.0배 / 성공 2.5배 (B안) |
| 약점이 겹칠 때 최종 배율 | ✅ r2 확정 | `GREATEST(약점+격돌, 기존 패턴×그로기)` (R2-2c-4) |
| 미입력 대표 / 도중 이탈 | ⚙ 설계 필요 | 정해진 노트 시한까지 MISS, 점수 합산 후 결과 확정 |
| 공명방벽 미활성 보스 | ⚙ r2 권장 | 방벽 ON 레이드에서만 격돌 활성화 허용(방벽 함수가 OFF면 예외 발생 확인) |
| 격돌 중 수동 일시정지 | ❓ r2 확인 필요 | 권장: 격돌 진행 중 교사 일시정지 차단(R2-4) |
| DB 스키마/함수 명명 | ⚙ 기술 선택 | 9장 권장안과 실제 DB를 비교해 결정 |

## 19. 최종 점검: 구현 완료 보고에 반드시 포함할 증거

Claude는 실제 개발 후 아래 항목을 파일·테스트 결과와 함께 제시할 것.

- [ ] 변경 파일 목록 및 영향 함수 목록(기존 함수 전/후 차이)
- [ ] 신규 마이그레이션 및 **운영 DB 적용 여부를 명확히 구분**
- [ ] 3난이도 독립 연습 스크린샷/시연 결과
- [ ] 5초 지원 → 1인 무작위 선정 → 8회 QTE → 결과 → 전투 재개 영상/로그
- [ ] HP50% 동시성 검증 및 재발동 방지 결과
- [ ] PERFECT/GOOD/BAD/MISS 판정 경계 테스트
- [ ] 5배/3.5배 합연산 피해 테스트
- [ ] 실패 시 **잔여 방벽 HP 기준 20%** 테스트
- [ ] 성공 시 10/16초 보스 일반공격 정지 및 시간 동결 정확성 테스트
- [ ] 기존 전리품 및 타격·패턴·속성·오디오 회귀 검사
- [ ] 24명 동시 참가 시 성능 결과
- [ ] 장애 복구 및 롤백 검증 결과
- [ ] 확인이 필요한 미확정 세부 정책 목록

**문서 작성 시점에서 격돌 기능 코드를 작성하거나 운영 DB에 배포하지 않았다.** 본 문서는 Claude Opus에 구현을 위임하기 위한 기획·기술 인수인계서이다.
